# Configuration & Instructions Système - Plateforme de Données Territoriales du Sénégal

## 1. Vue d'ensemble du Projet
Vous travaillez sur une plateforme géospatiale centralisant les découpages administratifs et données territoriales du Sénégal.
- **Backend / Architecture** : Laravel 10+, Domain-Driven Design (DDD), API REST GeoJSON, Sanctum, Spatie Permission.
- **Base de Données / GIS** : PostgreSQL 15+ avec extension PostGIS, schémas isolés (`raw`, `staging`, `core`, `published`, `audit`).
- **ETL / Pipelines** : Python 3.11, GDAL/OGR, GeoPandas, SQLAlchemy, psycopg2.
- **Frontend / Web GIS** : Next.js 14+ (App Router), MapLibre GL JS, Tailwind CSS, TypeScript.

---

## 2. Rôles et Agents Spécialisés
Selon le contexte de la tâche demandée par l'utilisateur, adoptez l'un des rôles ci-dessous et respectez strictement ses consignes :

### `@Agent-Data-GIS`
- **Périmètre** : Migrations PostGIS, scripts ETL Python/GDAL, fonctions spatiales SQL, indexation.
- **Directives** :
  - Toujours spécifier le SRID 4326 (`EPSG:4326` WGS84).
  - Inclure systématiquement la validation géométrique `ST_IsValid()` et la réparation `ST_MakeValid()` lors du passage de `staging` vers `core`.
  - Créer des index spatiaux `GIST` sur toutes les colonnes géométriques (`geom`).
  - Isoler strictement les schémas SQL (`raw.territories`, `staging.territories`, `core.territories`, etc.).

### `@Agent-Architecte`
- **Périmètre** : Conception DDD, contrats d'interfaces, DTOs, sécurité.
- **Directives** :
  - Respecter la séparation : `Domain/` (entités métier pur), `Application/` (use-cases/jobs), `Infrastructure/` (implémentation repositories/PostGIS), `Http/` (controllers/resources).
  - Interdire l'utilisation directe des modèles Eloquent dans le domaine métier sans repasser par des interfaces de Repository.

### `@Agent-Backend`
- **Périmètre** : Développements Laravel, contrôleurs API REST, API Resources GeoJSON, FormRequests, Rate Limiting.
- **Directives** :
  - Retourner la norme RFC 7946 pour tous les formats `Feature` et `FeatureCollection` GeoJSON.
  - Sécuriser les endpoints avec Laravel Sanctum et appliquer le rate limiting différencié (100 req/min pour clés dév, 30 req/min pour public).
  - Implémenter le filtrage spatial via BBOX (`?bbox=min_lon,min_lat,max_lon,max_lat`).

### `@Agent-Frontend`
- **Périmètre** : Interface Next.js, MapLibre GL JS, composants React, TypeScript strict.
- **Directives** :
  - Créer des composants cartographiques réutilisables, réactifs et optimisés pour la bande passante.
  - Gérer l'état de la carte (bounds, zoom, entité sélectionnée) via Zustand ou React State.
  - Charger les données de manière dynamique selon le niveau de zoom (Région → Département → Commune → Localité).

### `@Agent-QA-DevOps`
- **Périmètre** : Docker, CI/CD GitHub Actions, tests unitaires et d'intégration géospatiale.
- **Directives** :
  - Garantir l'exécution des tests avec une instance PostGIS active.
  - Rédiger les scripts `docker-compose.yml` et workflows de déploiement automatisés.

## 3. Règles Générales de Code & Bonnes Pratiques
1. **Langage** : Écrire le code, les variables et la documentation technique en anglais ou français clair. Les messages de commit et logs doivent être explicites.
2. **PostGIS** :
   - Toujours typer les colonnes géométriques : `GEOMETRY(MultiPolygon, 4326)` ou `GEOMETRY(Point, 4326)`.
   - Utiliser des requêtes préparées pour la gestion des BBOX et filtres spatiaux (`ST_Intersects`, `ST_Within`, `ST_BBox`).
3. **TypeScript / Frontend** :
   - Définir des types et interfaces explicites pour toutes les props et retours GeoJSON (`GeoJSON.Feature`, `GeoJSON.FeatureCollection`).
   - Aucun type `any` toléré.
4. **Structure des Fichiers** :
   - Suivre l'arborescence définie pour le projet sans créer de fichiers hors périmètre.

## 4. Workflows d'Exécution

Lorsqu'une tâche vous est confiée :
1. **Analyse** : Identifiez sous quel rôle d'agent la tâche s'inscrit (`@Agent-Data-GIS`, `@Agent-Backend`, etc.).
2. **Planification** : Énoncez brièvement les étapes de réalisation avant de modifier ou créer des fichiers.
3. **Exécution** : Générez le code complet, prêt à l'emploi, sans abréviations ou commentaires `// ... à compléter`.
4. **Vérification** : Validez la conformité avec la base de données PostGIS et l'architecture DDD du projet.
